# Лабораторные работы по ООП на C++20

Один репозиторий на семь лабораторных работ: от загрузки табличных данных до
анимированного градиентного спуска. Каждая работа опирается на код предыдущей.

Условия работ — в репозитории `OOP_Labs`.

## Сборка и запуск

Требуется CMake 3.24+ и компилятор с поддержкой C++20 (проверено на GCC 14.2).

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
```

Запуск приложения первой работы:

```bash
./build/apps/lab1/lab1
```

Тесты:

```bash
ctest --test-dir build --output-on-failure
```

Тесты собираются вместе с проектом. Чтобы собрать без них, есть два способа:

```bash
cmake --build build --target lab1                       # только приложение и ядро
cmake -S . -B build-notests -DOOP_BUILD_TESTS=OFF        # отдельная сборка без тестов
```

Конфигурация `Debug` (она же по умолчанию) собирается с AddressSanitizer и
UndefinedBehaviorSanitizer. Отключаются они флагом
`-DOOP_ENABLE_SANITIZERS=OFF`. Для замеров производительности нужна сборка
`-DCMAKE_BUILD_TYPE=Release`: под санитайзерами время выполнения не показательно.

## Структура репозитория

```text
core/          библиотека ядра: данные, статистика, преобразования, модели
  include/mlcore/ публичные заголовки, подключаются как "mlcore/....hpp"
  src/         реализация
apps/          консольные приложения, по подкаталогу на работу
  lab1/
tests/         тесты, по программе на файл, регистрируются в CTest
data/          датасет и результаты предобработки, в репозиторий не коммитятся
docs/
  agent_log/   журнал работы с ИИ-агентом по каждой работе
```

Граница между `core/` и `apps/`: ядро не знает про `std::cout` и аргументы
командной строки, всё взаимодействие с пользователем живёт в приложении.

Новый файл в `core/src/` попадает в сборку сам — список исходников собирается
через `file(GLOB CONFIGURE_DEPENDS)`. Новый тест нужно дописать одной строкой
`oop_add_test(имя)` в `tests/CMakeLists.txt`.

## Датасет

**Cirrhosis Patient Survival Prediction** — данные клинического исследования
первичного билиарного цирроза печени (Mayo Clinic, 1974–1984).

Источник: <https://archive.ics.uci.edu/dataset/878/cirrhosis+patient+survival+prediction+dataset+1>

### Пропущенные значения

Пропуск обозначается строкой `NA`. **Особый случай:** в столбце `Stage` шесть
пропусков записаны как `"NA"` — в двойных кавычках, тогда как во всех остальных
столбцах кавычек нет. Загрузчик снимает кавычки с поля до сравнения с
обозначением пропуска, иначе эти шесть значений были бы прочитаны как обычная
категория.

Пропуски есть в 10 признаках из 19, затронуто 142 объекта из 418:

| Признак | Пропусков | Доля |
|---|---|---|
| `Tryglicerides` | 136 | 32.5% |
| `Cholesterol` | 134 | 32.1% |
| `Copper` | 108 | 25.8% |
| `Drug`, `Ascites`, `Hepatomegaly`, `Spiders`, `Alk_Phos`, `SGOT` | 106 | 25.4% |
| `Platelets` | 11 | 2.6% |
| `Prothrombin` | 2 | 0.5% |

Пропуски не случайны: 106 пациентов не участвовали в клиническом исследовании,
и у них отсутствует вся группа связанных с ним измерений сразу.

## Работа 2. kNN

`IModel` — общий интерфейс `fit`/`predict`. `kNNBase` хранит общую часть,
`kNNRegressor` и `kNNClassifier` переопределяют агрегацию. Общая база позволяет
использовать один поиск соседей в обеих моделях. `IDistance` — стратегия:
модель владеет ею через `unique_ptr`; обучающие признаки и отклики копируются,
поэтому модель не зависит от времени жизни исходной выборки.

Для запроса с d признаками и n обучающими строками: O(n d + n log k) времени,
O(k) памяти поиска. Максимальная куча хранит худшего кандидата в вершине.
Равные расстояния разрешаются по меньшему индексу обучающей строки.
Классификатор при равных голосах выбирает меньшую числовую метку.

Веса задаются `Weighting::Uniform` (по умолчанию) или `Weighting::Distance`.
Двум фиксированным режимам достаточно enum, без отдельной иерархии.
Для обратных расстояний используется общий масштаб: ближайшее расстояние / текущее.
Он не меняет результат и избегает переполнения при вычислении обратной величины.
Если среди k соседей есть точные совпадения, остальные соседи исключаются:
регрессор усредняет совпадения, классификатор голосует только по ним.

По сравнению с работой 1 добавлены `span`-строки и проверяемый `at`,
`ModelMatrix` с несколькими откликами, совместное разбиение строк и ответов,
единый бинарный файл матрицы и откликов, собственные исключения.
Подробный формат и ограничения — в [описании API](docs/api.md).

### Демонстрация

Запускать из корня репозитория после сохранения данных первой работой:

```bash
./build/apps/lab2/lab2
```

Параметры задаются локально в `apps/lab2/main.cpp`: `k`, `weighting`,
`data_path`. Тип метрики выбирается внутри `make_metric`: например,
`std::make_unique<EuclideanDistance>()`, `ManhattanDistance` или
`ChebyshevDistance`. Фабрика создаёт отдельную метрику для каждой модели.
После изменения настроек приложение нужно пересобрать. Аргументы командной
строки не используются.

Показываются первые десять пар «настоящий ответ — предсказание» для N_Days
и Status. Разбиение: 0.7, seed=1. Сводные метрики качества здесь не считаются.

### Тесты и документация

CTest включает метрики, сравнение кучи с полной сортировкой, k=1,
ручные примеры весов, нулевые расстояния, ничьи, исключения и бинарный
цикл с двумя откликами. Обрезанный бинарный файл проверяется на каждой
границе байта. Ранее существовавшие тесты адаптированы к ModelMatrix.

Установив Doxygen, повторно выполнить конфигурацию CMake, затем:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target docs
```

Открыть `build/docs/html/index.html`. Обычная сборка не требует Doxygen.
В этой сессии документация собрана в `build-agent-lab2/docs/html/index.html`;
Doxygen запущен из временного каталога, в систему не установлен.

Комментарии описывают фактические предусловия: например, ColumnMajor пока
не реализован полностью, а стандартизация требует положительной дисперсии.
Эти ограничения документация не скрывает.
